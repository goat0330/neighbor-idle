# 协作规范

## 分支与 worktree

```bash
git worktree list
git worktree add "D:/WorkBuddy/2026-08-13-08-41-12/worktrees/workbuddy" workbuddy/develop
git worktree add "D:/WorkBuddy/2026-08-13-08-41-12/worktrees/codex" codex/develop
```

WorkBuddy 协作者只修改 `apps/workbuddy-app`；Codex 协作者只修改 `apps/codex-taro-app`。两边都可以继续组件化，但 WorkBuddy 和 Taro 的组件运行时不同，不直接复制组件实现；公共文档或接口契约需要在 issue/PR 中先说明，再由负责该模块的人修改。

## 提交与合并

- 提交格式：`feat(scope): ...`、`fix(scope): ...`、`docs(scope): ...`、`chore(scope): ...`。
- 每个 PR 只解决一个主题，标题写清楚版本和模块。
- 合并前至少通过对应版本的静态检查；涉及页面时补充真机/开发者工具截图。
- 不提交 `node_modules`、构建产物、`project.private.config.json`、密钥、真实用户数据。

## Figma 决策流程

Figma 是界面和交互的决策来源。拿到 Figma 文件链接或节点后，先记录页面、组件、变量和动效决策，再落到 `docs/figma/` 与 `src/design/`。没有 Figma 链接时，以当前已确认的 P3/P4 参考图建立临时设计契约，并在后续 Figma 文件接入后校准，不直接凭感觉覆盖设计。
